# PHR: update-project-constitution

## User Prompt

```
# /sp.constitution

## Project
**Evolution of Todo — Spec-Driven, AI-Native Todo Application**

A 5-Phase evolution of a Todo application built using **Spec-Driven Development**, **Claude Code**, and **Spec-Kit Plus**, culminating in an **AI-managed, cloud-native Todo system** with natural-language control.

---

## Core Principles

- **Spec-Driven Development First**
  - Every feature MUST begin with a written Spec.
  - No implementation without an approved Spec.
  - Specs are refined until Claude Code generates correct output.

- **Zero Manual Coding**
  - Human-written application code is strictly forbidden.
  - All source code MUST be generated by Claude Code from Specs.

- **Clean Architecture & Clean Code**
  - No duplicate directories, files, or logic.
  - One responsibility per file.
  - Explicit deletion of unused code, files, and directories.

- **Deterministic & Reproducible Builds**
  - Identical Specs must generate identical outputs.
  - No hidden state, no experimental leftovers.

- **AI-Native by Design**
  - Conversational control is a first-class feature, not an add-on.
  - Natural language commands must map deterministically to Todo actions.

---

## Mandatory Development Standards

### Spec Standards
- Every Phase MUST contain:
  - A **Phase Constitution**
  - Feature-level **Markdown Specs**
- Specs must define:
  - Inputs
  - Outputs
  - Edge cases
  - Failure behavior
  - Acceptance criteria

### Code Quality Rules
- ❌ No duplicate logic across files
- ❌ No duplicate directories for similar concerns
- ❌ No commented-out code
- ❌ No unused imports
- ❌ No temporary utilities left behind

If something is:
- Replaced → **DELETE the old file**
- Deprecated → **DELETE the directory**
- Used only for testing → **DELETE after validation**

---

## Phase Requirements

### Phase I — Basic Todo (Spec-Only Foundation)
- Core Todo CRUD functionality
- No AI
- No chatbot
- Local execution only
- Strict Spec → Code generation loop

### Phase II — Advanced Todo Logic
- Scheduling
- Priorities
- Status transitions
- Validation rules defined ONLY in Specs

### Phase III — AI Conversational Interface
- Integrate:
  - OpenAI ChatKit
  - OpenAI Agents SDK
  - Official MCP SDK
- Natural language Todo control
  - Example:
    > "Move all my low-priority tasks to tomorrow morning"
- AI behavior must be fully Spec-defined (no implicit logic)

### Phase IV — Local Cloud-Native Deployment
- Deploy on **Minikube**
- Kubernetes manifests generated via Specs
- AI chatbot fully operational in cluster
- No local-only shortcuts

### Phase V — Production Cloud Deployment
- Deploy to **DigitalOcean Kubernetes (DOKS)**
- Production-grade configuration
- Secure environment variables
- Clean teardown instructions included

---

## AI Chatbot Constraints

- The chatbot:
  - MUST NOT hallucinate Todo state
  - MUST operate only on persisted data
  - MUST confirm destructive actions
- Every natural-language intent:
  - Must map to a defined Spec action
  - Must have deterministic execution

---

## File & Directory Governance

- Single source of truth per concern
- No parallel implementations
- No `/temp`, `/test`, `/debug`, or `/experiment` folders in final state
- If tests are created:
  - They MUST be deleted after validation unless explicitly required

---

## Deployment Rules

- Kubernetes YAML must be:
  - Minimal
  - Readable
  - Non-duplicated
- No environment-specific hacks
- Minikube ≠ DOKS configs must be explicitly separated and documented

---

## Constraints

- ❌ No manual code writing
- ❌ No skipped phases
- ❌ No partial Specs
- ❌ No leftover test artifacts
- ❌ No duplicate code or folders

---

## Success Criteria

- All 5 Phases completed
- Every feature traceable to a Spec
- Zero duplicate files or directories
- Clean repository tree
- AI chatbot fully functional in Phases III–V
- Successful deployment on:
  - Minikube
  - DigitalOcean Kubernetes (DOKS)
```
